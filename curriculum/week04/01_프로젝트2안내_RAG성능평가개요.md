## 📚 2. Advanced RAG 개요

### 2.1 기본 RAG vs Advanced RAG

기본 RAG(Naive RAG)는 단순히 쿼리를 임베딩하여 유사한 문서를 검색하고 LLM에 전달하는 방식입니다. 반면 **Advanced RAG**는 검색 전(Pre-Retrieval), 검색 중(Retrieval), 검색 후(Post-Retrieval) 각 단계에서 추가적인 최적화를 적용합니다.

```
┌─────────────────────────────────────────────────────────────┐
│          Naive RAG vs Advanced RAG 비교                      │
│                                                              │
│  Naive RAG:                                                  │
│  쿼리 → [임베딩] → [벡터 검색] → [LLM] → 답변              │
│                                                              │
│  Advanced RAG:                                               │
│                                                              │
│  Pre-Retrieval:   쿼리 → [쿼리 확장/재작성]                  │
│                         ↓                                    │
│  Retrieval:            [하이브리드 검색]                      │
│                    BM25 ──┐                                  │
│                           ├→ [RRF Fusion]                   │
│                  Vector ──┘                                  │
│                         ↓                                    │
│  Post-Retrieval:       [Re-ranking]                          │
│                        [맥락 압축]                            │
│                         ↓                                    │
│                        [LLM] → 답변                          │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 Advanced RAG의 세 가지 패러다임

**1. Modular RAG (모듈식 RAG)**
- 검색, 생성 등 각 컴포넌트를 독립적으로 교체 가능
- 파이프라인 유연성 극대화

**2. Iterative RAG (반복적 RAG)**
- 여러 번의 검색-생성 사이클 반복
- 복잡한 다단계 질문 처리

**3. Adaptive RAG (적응형 RAG)**
- 질문 복잡도에 따라 검색 전략 동적 선택
- Self-RAG: LLM이 검색 필요 여부를 스스로 판단

### 2.3 Advanced RAG 주요 기법 분류

```
Advanced RAG 기법 체계
│
├── Pre-Retrieval (검색 전)
│   ├── 쿼리 재작성 (Query Rewriting)
│   ├── 쿼리 확장 (Query Expansion)
│   │   ├── Multi-Query
│   │   ├── HyDE
│   │   └── RAG-Fusion
│   └── 쿼리 분해 (Query Decomposition)
│
├── Retrieval (검색 중)
│   ├── 하이브리드 검색
│   │   ├── BM25 + Vector Search
│   │   └── RRF (Reciprocal Rank Fusion)
│   └── 청크 전략 최적화
│       ├── Semantic Chunking
│       └── Parent-Child Chunking
│
└── Post-Retrieval (검색 후)
    ├── Re-ranking
    │   ├── Cross-Encoder
    │   └── Cohere Reranker
    └── 맥락 압축
        ├── LLMChainExtractor
        └── EmbeddingsFilter
```

## 📚 3. RAG 성능 평가의 필요성

### 3.1 왜 RAG 시스템을 평가해야 하는가?

RAG 시스템은 두 가지 핵심 컴포넌트(검색 엔진 + LLM)가 결합된 복합 시스템입니다. 각 컴포넌트의 성능이 최종 답변 품질에 영향을 미치므로, **어느 부분이 병목인지** 파악하기 위해 체계적인 평가가 필수입니다.

```
RAG 실패 유형 분석
┌─────────────────────────────────────────────┐
│                                              │
│  실패 유형 1: 검색 실패 (Retrieval Failure)  │
│  ─ 올바른 문서가 검색되지 않음               │
│  ─ 증상: 관련 없는 답변, 환각(Hallucination) │
│  ─ 해결: 하이브리드 검색, 쿼리 확장          │
│                                              │
│  실패 유형 2: 생성 실패 (Generation Failure) │
│  ─ 올바른 문서를 검색했지만 잘못된 답변      │
│  ─ 증상: 맥락 무시, 부정확한 요약            │
│  ─ 해결: 프롬프트 개선, LLM 교체             │
│                                              │
│  실패 유형 3: 맥락 노이즈 (Context Noise)   │
│  ─ 관련 없는 문서가 맥락에 포함됨            │
│  ─ 증상: 답변 혼동, 오정보 생성              │
│  ─ 해결: Re-ranking, 맥락 압축               │
│                                              │
└─────────────────────────────────────────────┘
```

### 3.2 평가 없는 RAG 개선의 위험성

💡 **핵심 포인트**: "측정할 수 없으면 개선할 수 없다" (피터 드러커)

RAG 시스템 개선 시 평가 없이 직관만으로 작업하면:
- 특정 케이스 개선이 다른 케이스 성능 저하를 야기할 수 있음
- 청크 크기 변경이 일부 쿼리는 개선하고 다른 쿼리는 악화시킬 수 있음
- A/B 테스트 없이는 실제 효과를 알 수 없음

## 📚 4. 평가 지표 개요: 검색 vs 답변

### 4.1 RAG 평가의 두 축

```
┌─────────────────────────────────────────────────────────────┐
│                   RAG 평가 지표 체계                          │
│                                                              │
│  ┌─────────────────────┐    ┌─────────────────────────┐     │
│  │   검색 성능 평가     │    │    답변 품질 평가         │     │
│  │  (Retrieval)        │    │    (Generation)           │     │
│  │                     │    │                           │     │
│  │  • Hit Rate (HR@K)  │    │  • Faithfulness           │     │
│  │  • MRR              │    │  • Answer Relevancy       │     │
│  │  • NDCG             │    │  • Context Recall         │     │
│  │  • MAP              │    │  • Context Precision      │     │
│  │                     │    │  • BLEU / ROUGE           │     │
│  │  "올바른 문서를      │    │  • BERTScore              │     │
│  │   찾았는가?"         │    │  "올바른 답변을           │     │
│  │                     │    │   생성했는가?"             │     │
│  └─────────────────────┘    └─────────────────────────┘     │
│          Week 4                        Week 5                │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 RAGAS의 핵심 지표

RAGAS(RAG Assessment)는 RAG 시스템의 4가지 핵심 지표를 정의합니다:

| 지표 | 설명 | 범위 |
|------|------|------|
| **Faithfulness** | 답변이 검색된 맥락에 충실한가? | 0~1 |
| **Answer Relevancy** | 답변이 질문에 관련있는가? | 0~1 |
| **Context Recall** | 정답에 필요한 맥락이 검색되었는가? | 0~1 |
| **Context Precision** | 검색된 맥락 중 관련있는 비율 | 0~1 |

## 📚 5. 평가 프레임워크 소개

### 5.1 RAGAS (RAG Assessment)

RAGAS는 RAG 파이프라인을 자동으로 평가하는 오픈소스 프레임워크입니다.

```python
# RAGAS 기본 사용 예시
from ragas import evaluate
from ragas.metrics import (
    faithfulness,
    answer_relevancy,
    context_recall,
    context_precision
)

# 평가 데이터셋 구성
from datasets import Dataset

data = {
    "question": ["ETF란 무엇인가요?"],
    "answer": ["ETF는 주식처럼 거래되는 펀드입니다..."],
    "contexts": [["ETF(Exchange-Traded Fund)는..."]],
    "ground_truth": ["ETF는 거래소에서 거래되는 인덱스 펀드..."]
}
dataset = Dataset.from_dict(data)

# 평가 실행
result = evaluate(
    dataset=dataset,
    metrics=[faithfulness, answer_relevancy, context_recall, context_precision]
)
print(result)
```

**RAGAS 아키텍처:**
```
RAGAS 평가 파이프라인
┌─────────────────────────────────────────┐
│                                          │
│  입력:                                   │
│  - 질문 (Question)                       │
│  - 검색된 맥락 (Contexts)               │
│  - 생성된 답변 (Answer)                 │
│  - 정답 (Ground Truth) [선택적]          │
│                                          │
│  평가 LLM이 각 지표를 자동 계산          │
│                                          │
│  출력:                                   │
│  - Faithfulness: 0.87                   │
│  - Answer Relevancy: 0.92               │
│  - Context Recall: 0.78                 │
│  - Context Precision: 0.83              │
│  - RAGAS Score: 0.85                    │
│                                          │
└─────────────────────────────────────────┘
```

### 5.2 DeepEval

DeepEval은 LLM 앱을 위한 단위 테스트 프레임워크로, pytest와 유사한 방식으로 테스트를 작성합니다.

```python
# DeepEval 기본 사용 예시
from deepeval import assert_test
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric
from deepeval.test_case import LLMTestCase

# 테스트 케이스 정의
test_case = LLMTestCase(
    input="ETF 투자 시 고려해야 할 비용은?",
    actual_output="ETF 투자 시 운용보수(TER), 거래세, 거래 수수료를 고려해야 합니다.",
    retrieval_context=["ETF의 총비용비율(TER)은 일반적으로 0.03~0.5% 수준..."]
)

# 지표 정의
metric = AnswerRelevancyMetric(threshold=0.7)

# 테스트 실행
assert_test(test_case, [metric])
```

### 5.3 TruLens

TruLens는 LLM 앱의 피드백 기반 평가를 제공합니다. 특히 **RAG Triad** 개념을 도입했습니다.

```
TruLens RAG Triad
┌─────────────────────────────────────────────────────────┐
│                                                          │
│         질문 (Query)                                     │
│           ↙           ↘                                  │
│  Answer           Context                                │
│  Relevance        Relevance                              │
│    ↘           ↙                                         │
│       Groundedness                                       │
│                                                          │
│  • Answer Relevance: 답변이 질문에 관련있는가?            │
│  • Context Relevance: 검색된 맥락이 질문에 관련있는가?   │
│  • Groundedness: 답변이 맥락에 근거하는가?               │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

## 📚 6. 테스트셋 구축 방법

### 6.1 테스트셋의 중요성

좋은 평가는 좋은 테스트셋에서 시작합니다. 테스트셋이 실제 사용 패턴을 반영하지 못하면, 높은 평가 점수가 무의미해집니다.

```
테스트셋 구축 프로세스
┌─────────────────────────────────────────────────────────┐
│                                                          │
│  Step 1: 실제 사용자 쿼리 수집 (가능하다면)              │
│  Step 2: 도메인 전문가 질문 작성                         │
│  Step 3: LLM으로 합성 질문 생성 (다양성 확보)            │
│  Step 4: 질문 유형 분류 (사실형, 추론형, 비교형 등)      │
│  Step 5: Ground Truth 답변 작성 (전문가 검토)            │
│  Step 6: 품질 검증 및 필터링                             │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 6.2 RAGAS를 활용한 테스트셋 자동 생성

```python
# RAGAS TestsetGenerator 활용
from ragas.testset.generator import TestsetGenerator
from ragas.testset.evolutions import simple, reasoning, multi_context
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain.document_loaders import DirectoryLoader

# 문서 로드
loader = DirectoryLoader("./etf_documents/")
documents = loader.load()

# 테스트셋 생성기 초기화
generator_llm = ChatOpenAI(model="gpt-4o-mini")
critic_llm = ChatOpenAI(model="gpt-4o")
embeddings = OpenAIEmbeddings()

generator = TestsetGenerator.from_langchain(
    generator_llm,
    critic_llm,
    embeddings
)

# 테스트셋 생성 (10개 샘플)
testset = generator.generate_with_langchain_docs(
    documents,
    test_size=10,
    distributions={
        simple: 0.5,        # 단순 사실 질문 50%
        reasoning: 0.3,     # 추론 필요 질문 30%
        multi_context: 0.2  # 다중 맥락 질문 20%
    }
)
```

### 6.3 질문 유형 분류 체계

## 🔍 심화학습

### Self-RAG: LLM이 스스로 판단하는 RAG

Self-RAG는 LLM이 검색 필요 여부, 검색 결과의 관련성, 답변의 품질을 스스로 평가하는 접근법입니다.

```
Self-RAG 흐름도
쿼리 입력
   │
   ▼
[검색 필요 여부 판단] ──No──→ [LLM 직접 답변]
   │Yes
   ▼
[문서 검색]
   │
   ▼
[관련성 평가] ──Not Relevant──→ [재검색]
   │Relevant
   ▼
[답변 생성]
   │
   ▼
[답변 품질 자기 평가]
   │
   ├─ Supported: 최종 답변 반환
   └─ Not Supported: 재생성
```

### CRAG (Corrective RAG)

검색 결과가 부적절할 경우 웹 검색으로 보완하는 기법:

```python
# CRAG 개념적 구현
def crag_pipeline(query, retriever, web_searcher, llm):
    # 1. 벡터 DB 검색
    docs = retriever.get_relevant_documents(query)

    # 2. 관련성 평가
    relevance_scores = evaluate_relevance(query, docs)

    if max(relevance_scores) > 0.7:
        # 충분히 관련있는 문서 발견
        context = prepare_context(docs)
    elif max(relevance_scores) > 0.3:
        # 부분적으로 관련 - 웹 검색 보완
        web_docs = web_searcher.search(query)
        context = prepare_context(docs + web_docs)
    else:
        # 관련없는 문서 - 웹 검색 전적 의존
        web_docs = web_searcher.search(query)
        context = prepare_context(web_docs)

    return llm.generate(query, context)
```

## 💡 핵심 포인트

1. **평가 없이는 개선 없다**: RAG 시스템의 어느 부분이 문제인지 파악하려면 체계적인 평가가 필수
2. **검색과 생성은 별도 평가**: 검색 단계와 생성 단계의 문제를 분리하여 진단
3. **테스트셋 품질이 평가 품질**: 실제 사용 패턴을 반영한 다양한 질문 유형 포함
4. **비용 효율적 전략**: 모든 것을 GPT-4o로 평가하면 비용이 폭발적으로 증가
5. **연속적 평가**: 시스템 변경 시마다 평가를 반복하여 회귀 방지

## ⚠️ 주의사항

- **평가 지표의 과신 금지**: RAGAS 점수가 높아도 실제 사용자 만족도와 다를 수 있음
- **분포 이동(Distribution Shift)**: 테스트셋이 실제 쿼리 분포와 다르면 평가가 무의미
- **LLM 평가자의 편향**: GPT-4로 평가 시 GPT-4가 생성한 답변에 유리할 수 있음 (자기 편향)
- **Ground Truth의 한계**: 금융 도메인에서 "정답"이 하나가 아닐 수 있음
