## 📚 1. 키워드 검색 (BM25) 알고리즘 원리

### 1.1 TF-IDF에서 BM25로의 진화

키워드 검색의 역사는 TF-IDF(Term Frequency - Inverse Document Frequency)에서 시작합니다. BM25(Best Match 25)는 TF-IDF의 단점을 개선한 정보 검색 알고리즘으로, **Okapi BM25**라고도 불립니다.

```
TF-IDF의 한계
┌─────────────────────────────────────────────────────────────┐
│  문제 1: TF 포화 (Term Frequency Saturation)                │
│  - "ETF"가 문서에 1번 나오든 100번 나오든                   │
│    점수가 비례하여 증가 (현실적이지 않음)                    │
│  - 실제로는 1번 나온 것과 10번 나온 것의 차이가              │
│    1번과 100번의 차이보다 훨씬 큼                            │
│                                                              │
│  문제 2: 문서 길이 미반영                                    │
│  - 긴 문서는 단어를 많이 포함 → TF 높아짐                  │
│  - 실제로는 긴 문서가 더 "관련있다"고 볼 수 없음            │
│                                                              │
│  BM25가 해결하는 방법:                                       │
│  1. TF 포화 처리: k1 파라미터로 TF 포화 조절                │
│  2. 길이 정규화: b 파라미터로 문서 길이 영향 조절            │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 BM25 공식 상세 설명

```
BM25 공식:

          N - df(t) + 0.5                    tf(t,d) × (k1 + 1)
IDF(t) = ─────────────────── + 1     TF = ──────────────────────────────────
          df(t) + 0.5                       tf(t,d) + k1 × (1 - b + b × |d|/avgdl)

BM25 Score(q, d) = Σ IDF(t) × TF(t,d)
                   t∈q

파라미터 설명:
─────────────────────────────────────────────────────────────
  N      = 전체 문서 수
  df(t)  = 단어 t를 포함하는 문서 수 (Document Frequency)
  tf(t,d)= 문서 d에서 단어 t의 출현 횟수
  |d|    = 문서 d의 길이 (단어 수)
  avgdl  = 평균 문서 길이
  k1     = TF 포화 파라미터 (일반적으로 1.2~2.0)
           → 클수록 TF의 영향이 커짐
  b      = 길이 정규화 파라미터 (0~1, 일반적으로 0.75)
           → 1에 가까울수록 길이 정규화 강함
           → 0이면 길이 정규화 없음
─────────────────────────────────────────────────────────────
```

### 1.3 k1과 b 파라미터의 영향

```
k1 파라미터 효과 (b=0.75 고정):
tf  │ k1=0.5  │ k1=1.2  │ k1=2.0  │ TF-IDF
────┼─────────┼─────────┼─────────┼─────────
 1  │  0.600  │  0.688  │  0.750  │  1.000
 2  │  0.800  │  0.850  │  0.900  │  2.000
 5  │  0.923  │  0.953  │  0.972  │  5.000
10  │  0.952  │  0.968  │  0.978  │ 10.000
20  │  0.976  │  0.984  │  0.989  │ 20.000

→ BM25의 TF는 포화되어 어느 값 이상을 넘지 않음
→ TF-IDF는 무한히 증가

b 파라미터 효과 (k1=1.2 고정):
문서 길이가 평균의 2배일 때:
  b=0.0: 길이 페널티 없음 → 긴 문서 유리
  b=0.5: 중간 길이 정규화
  b=1.0: 완전 길이 정규화 → 긴 문서 페널티
```

## 📚 3. 의미 검색 (Semantic Search) vs 키워드 검색

### 3.1 두 방식의 근본적 차이

```
의미 검색 vs 키워드 검색 비교
┌─────────────────────────────────────────────────────────────┐
│                                                              │
│  키워드 검색 (BM25):                                         │
│  쿼리: "저렴한 ETF 투자"                                    │
│  → "ETF", "투자", "저렴한" 단어가 있는 문서 검색            │
│  장점: 정확한 용어 매칭, 빠른 속도, 적은 리소스             │
│  단점: 동의어/유사어 처리 불가                               │
│        "수수료 낮은 ETF"는 검색 못 할 수 있음               │
│                                                              │
│  의미 검색 (Vector):                                         │
│  쿼리: "저렴한 ETF 투자"                                    │
│  → 쿼리를 임베딩 → 유사한 벡터의 문서 검색                  │
│  → "수수료 낮은 ETF", "비용 효율적 인덱스 펀드" 등 검색    │
│  장점: 의미적 유사성 포착, 언어 다양성 처리                  │
│  단점: 정확한 숫자/코드 검색 취약, 높은 리소스              │
│                                                              │
│  하이브리드:                                                 │
│  → 두 방식의 장점 결합                                      │
│  → "저렴한" = 의미 유사성 + "ETF" = 정확 키워드 매칭        │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 각 방식이 유리한 케이스

| 케이스 | 키워드(BM25) | 의미(Vector) |
|--------|-------------|-------------|
| "QQQ ETF" (정확한 티커) | ✅ 강력 | ❌ 약함 |
| "기술주에 투자하는 미국 ETF" | ❌ 약함 | ✅ 강력 |
| 금융 용어 검색 | ✅ 강력 | ⚠️ 보통 |
| 개념 설명 질문 | ⚠️ 보통 | ✅ 강력 |
| 숫자/수식 포함 | ✅ 강력 | ❌ 약함 |
| 다국어 검색 | ❌ 약함 | ✅ 강력 |

## 📚 5. RRF (Reciprocal Rank Fusion) 알고리즘

### 5.1 RRF 개념

RRF는 여러 순위 목록을 하나로 합치는 알고리즘입니다. 각 결과의 순위에 기반한 점수를 합산합니다.

```
RRF 공식:
                    1
RRF(d) = Σ  ─────────────────
         r∈R  k + rank_r(d)

k = 상수 (일반적으로 60)
rank_r(d) = 순위 목록 r에서 문서 d의 순위
R = 순위 목록의 집합
```

### 5.2 RRF 계산 예시

```
RRF 계산 예시 (k=60)
────────────────────────────────────────────────────────────
문서     BM25 순위  Vector 순위  RRF 점수
────────────────────────────────────────────────────────────
Doc_A     1위         3위        1/(60+1) + 1/(60+3)
                                = 0.01639 + 0.01587 = 0.03226
Doc_B     2위         5위        1/(60+2) + 1/(60+5)
                                = 0.01613 + 0.01538 = 0.03151
Doc_C     없음        1위        0 + 1/(60+1) = 0.01639
Doc_D     3위         없음       1/(60+3) + 0 = 0.01587
────────────────────────────────────────────────────────────

최종 순위: Doc_A > Doc_B > Doc_C > Doc_D

핵심 원리:
- 두 검색 방식 모두에서 높은 순위 = 높은 RRF 점수
- 한쪽에만 있어도 점수는 받지만 낮음
- k=60은 낮은 순위들의 점수 차이를 완화하는 역할
────────────────────────────────────────────────────────────
```

## 📚 6. EnsembleRetriever 활용

### 6.1 LangChain EnsembleRetriever 구조

```
EnsembleRetriever 아키텍처
┌─────────────────────────────────────────────────────────────┐
│                                                              │
│  쿼리                                                        │
│    │                                                         │
│    ├──────────────────────┐                                  │
│    │                       │                                 │
│    ▼                       ▼                                 │
│  BM25Retriever           VectorRetriever                    │
│  (가중치: 0.5)            (가중치: 0.5)                      │
│    │                       │                                 │
│    ▼                       ▼                                 │
│  [Doc3, Doc1, Doc5, ...]  [Doc1, Doc4, Doc2, ...]          │
│    │                       │                                 │
│    └──────────┬────────────┘                                │
│               ▼                                              │
│        RRF Fusion                                            │
│               ▼                                              │
│      최종 순위 결과                                           │
│      [Doc1, Doc3, Doc4, Doc5, Doc2, ...]                   │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

```python
from langchain.retrievers import BM25Retriever, EnsembleRetriever
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings

# 예시 ETF 문서들
docs = [...]  # Document 객체 목록

# BM25 Retriever 생성
bm25_retriever = BM25Retriever.from_documents(docs)
bm25_retriever.k = 5  # 상위 5개 반환

# Vector Retriever 생성
embeddings = OpenAIEmbeddings()
vectorstore = Chroma.from_documents(docs, embeddings)
vector_retriever = vectorstore.as_retriever(search_kwargs={"k": 5})

# Ensemble Retriever (동일 가중치)
ensemble_retriever = EnsembleRetriever(
    retrievers=[bm25_retriever, vector_retriever],
    weights=[0.5, 0.5]
)

# 검색 실행
results = ensemble_retriever.get_relevant_documents("기술주 ETF 추천")
```

## 📚 8. 한국어 형태소 분석기 연동

### 8.1 한국어 BM25의 도전

한국어는 교착어(agglutinative language)로, 어근 + 조사/어미가 붙어서 다양한 형태로 변형됩니다. 따라서 단순 공백 분리로는 정확한 키워드 매칭이 어렵습니다.

```
한국어 형태소 분석 필요성
────────────────────────────────────────────────────────────
공백 분리:
"ETF에 투자하는 방법은?" → ["ETF에", "투자하는", "방법은?"]

형태소 분석:
"ETF에 투자하는 방법은?" → ["ETF", "에", "투자", "하는", "방법", "은", "?"]
불용어 제거 후: ["ETF", "투자", "방법"]

더 좋은 매칭:
"ETF 투자 방법 알려주세요" 검색 시 위 문서 찾기 가능
────────────────────────────────────────────────────────────
```

### 8.2 Konlpy 활용

```python
# pip install konlpy
from konlpy.tag import Okt, Kkma, Mecab

# Okt (Open Korean Text) - 가장 가볍고 빠름
okt = Okt()

def tokenize_korean_okt(text: str) -> list:
    """Okt를 사용한 한국어 형태소 분석"""
    tokens = okt.pos(text, norm=True, stem=True)
    # 명사, 동사, 형용사만 추출 (불용어 제거)
    meaningful_pos = {"Noun", "Verb", "Adjective"}
    return [
        word for word, pos in tokens
        if pos in meaningful_pos and len(word) > 1
    ]

# Mecab - 속도와 정확도 균형 (환경 설정 필요)
# pip install python-mecab-ko
try:
    mecab = Mecab()
    def tokenize_korean_mecab(text: str) -> list:
        """Mecab을 사용한 형태소 분석"""
        tokens = mecab.pos(text)
        # NNG(일반명사), NNP(고유명사), VV(동사), VA(형용사)
        target_pos = {"NNG", "NNP", "VV", "VA"}
        return [
            word for word, pos in tokens
            if pos in target_pos
        ]
except:
    print("Mecab을 사용할 수 없습니다. Okt를 사용합니다.")
```

### 8.3 한국어 BM25 커스텀 토크나이저

```python
from rank_bm25 import BM25Okapi
from konlpy.tag import Okt

class KoreanBM25Retriever:
    """한국어 형태소 분석기 + BM25 검색기"""

    def __init__(self, documents: list, k1: float = 1.5, b: float = 0.75):
        self.okt = Okt()
        self.documents = documents
        self.k = 5  # 기본 반환 문서 수

        # 형태소 분석으로 토크나이징
        tokenized_corpus = [
            self._tokenize(doc.page_content)
            for doc in documents
        ]
        self.bm25 = BM25Okapi(tokenized_corpus, k1=k1, b=b)

    def _tokenize(self, text: str) -> list:
        """한국어 텍스트 형태소 분석"""
        tokens = self.okt.pos(text, norm=True, stem=True)
        return [
            word for word, pos in tokens
            if pos in {"Noun", "Verb", "Adjective"} and len(word) > 1
        ]

    def get_relevant_documents(self, query: str) -> list:
        """쿼리에 관련된 문서 반환"""
        tokenized_query = self._tokenize(query)
        scores = self.bm25.get_scores(tokenized_query)

        # 점수 순으로 정렬
        ranked_idx = sorted(range(len(scores)), key=lambda i: scores[i], reverse=True)
        return [self.documents[i] for i in ranked_idx[:self.k]]
```

## 🔍 심화학습

### SPLADE (Sparse Lexical and Expansion Model)

SPLADE는 BERT 기반의 희소 벡터 모델로, BM25의 희소성과 Dense 모델의 의미 이해 능력을 결합합니다.

```
SPLADE의 특징:
- 각 단어를 희소 벡터로 표현 (대부분 0, 일부만 활성)
- BERT의 Masked Language Model 활용
- 쿼리 확장 효과 내포 (관련 단어 자동 추가)
- BM25보다 높은 성능, Dense 모델보다 빠른 검색
```

### ColBERT (Contextualized Late Interaction)

ColBERT는 문서의 모든 토큰을 임베딩하여 늦은 상호작용(Late Interaction)으로 점수를 계산합니다.

```
ColBERT MaxSim 연산:
Score(q,d) = Σ  max  (qi · dj)
             i   j

→ 쿼리의 각 토큰이 문서 내 가장 유사한 토큰과 매칭
→ BM25와 Dense의 장점을 모두 포함
```

## 💡 핵심 포인트

1. **BM25는 여전히 강력**: 의미 검색이 주목받지만 정확한 키워드 매칭에서 BM25가 우수
2. **하이브리드가 표준**: 대부분의 프로덕션 RAG 시스템은 하이브리드 검색 사용
3. **RRF의 k=60**: 이 상수는 경험적으로 잘 작동하지만 도메인에 따라 조정 가능
4. **한국어는 특별 처리**: 형태소 분석 없는 BM25는 한국어에서 성능 저하
5. **가중치는 실험으로**: 이론적인 최적 가중치는 없고 데이터로 결정

## ⚠️ 주의사항

- **메모리 사용량**: BM25는 역색인을 메모리에 저장 → 대용량 코퍼스에서 메모리 주의
- **인코딩 이슈**: 한국어 처리 시 UTF-8 인코딩 확인 필수
- **Konlpy 설치**: Java 의존성 있음 → JDK 설치 필요
- **동음이의어**: 형태소 분석만으로는 "배(ship)"와 "배(pear)" 구분 어려움
- **EnsembleRetriever의 k**: 각 Retriever의 k를 충분히 크게 설정해야 RRF가 효과적
