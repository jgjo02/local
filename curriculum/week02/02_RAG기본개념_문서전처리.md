## 1. RAG란?

### 1.1 정의

**RAG (Retrieval Augmented Generation)**:
외부 지식 베이스에서 관련 정보를 검색(Retrieve)하여 LLM의 답변 생성(Generate)을 보강(Augment)하는 기법

```
Before RAG (LLM alone):
  질문: "우리 회사의 2024년 매출은?"
  LLM: "죄송합니다, 해당 정보가 없습니다" (또는 환각)

After RAG:
  질문: "우리 회사의 2024년 매출은?"
  검색: 내부 문서에서 관련 정보 검색
  LLM: "2024년 매출은 1,250억 원으로, 전년 대비 18% 증가했습니다"
```

### 1.2 RAG vs Fine-tuning vs Prompt Stuffing

| 방법 | 장점 | 단점 | 적합 케이스 |
|------|------|------|-----------|
| RAG | 실시간 정보 반영, 비용 효율 | 검색 품질에 의존 | 방대한 문서, 자주 변경 |
| Fine-tuning | 도메인 특화 성능 | 비용 높음, 재학습 필요 | 고정된 지식, 특정 스타일 |
| Prompt Stuffing | 구현 간단 | 컨텍스트 제한, 비용 | 소량 문서 |

### 1.3 RAG가 필요한 이유

```
LLM의 한계:
1. 학습 데이터 시점 한계 (Knowledge Cutoff)
2. 기업 내부 정보 없음
3. 환각(Hallucination) 발생
4. 소스 인용 불가

RAG로 해결:
1. 최신 문서 반영 가능
2. 기업 내부 문서 활용 가능
3. 검색된 문서 기반 답변 → 환각 감소
4. 소스 문서 인용 가능
```

## 2. RAG 파이프라인 전체 구조

### 2.1 두 단계: Indexing & Querying

```
═══════════════════════════════════════════════════════════════
                    INDEXING (사전 준비)
═══════════════════════════════════════════════════════════════

원본 문서들
(PDF, TXT, CSV...)
      │
      ▼
┌─────────────┐
│  문서 로더   │  PyPDFLoader, TextLoader, WebBaseLoader
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  텍스트 분할 │  RecursiveCharacterTextSplitter
│  (청킹)     │  chunk_size=1000, overlap=200
└──────┬──────┘
       │  [청크1, 청크2, 청크3, ...]
       ▼
┌─────────────┐
│  임베딩 모델 │  OpenAI, BAAI/bge-m3
└──────┬──────┘
       │  [벡터1, 벡터2, 벡터3, ...]
       ▼
┌─────────────┐
│  벡터 저장소 │  FAISS, Chroma, Pinecone
└─────────────┘

═══════════════════════════════════════════════════════════════
                    QUERYING (실시간 검색)
═══════════════════════════════════════════════════════════════

사용자 질문
      │
      ▼
┌─────────────┐
│  임베딩 모델 │  질문을 벡터로 변환
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  유사도 검색 │  Top-K 관련 청크 검색
│  (Retrieve) │
└──────┬──────┘
       │  관련 청크 3-5개
       ▼
┌─────────────┐
│  프롬프트   │  컨텍스트 + 질문 조합
│  구성       │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│     LLM     │  답변 생성
└──────┬──────┘
       │
       ▼
    최종 답변
```

## 3. 문서 전처리

### 3.1 전처리가 중요한 이유

```
원본 PDF 텍스트 추출 예시:
"제 3 조 ( 계 약 의 성 립 )  ①  계  약  은  청   약 과  승  낙 으 로 ..."
               ↓ 전처리
"제3조(계약의 성립) ① 계약은 청약과 승낙으로..."

전처리 없이 임베딩 → 품질 저하!
```

### 3.2 기본 텍스트 정규화

```python
import re

def normalize_text(text: str) -> str:
    """기본 텍스트 정규화"""
    # 불필요한 공백 제거
    text = re.sub(r'\s+', ' ', text)
    # 특수문자 정리 (필요한 것만 유지)
    text = re.sub(r'[^\w\s가-힣.,!?;:()\-]', '', text)
    # 앞뒤 공백 제거
    text = text.strip()
    return text
```

### 3.3 PDF 특유의 노이즈 제거

```python
def clean_pdf_text(text: str) -> str:
    """PDF 추출 텍스트 정리"""
    # 페이지 번호 패턴 제거 (예: "- 5 -", "5 / 10")
    text = re.sub(r'[-–]\s*\d+\s*[-–]', '', text)
    text = re.sub(r'\d+\s*/\s*\d+', '', text)
    # 헤더/푸터 반복 패턴 제거
    text = re.sub(r'Copyright.*?\n', '', text)
    # 연속 줄바꿈 정리
    text = re.sub(r'\n{3,}', '\n\n', text)
    return text.strip()
```

## 4. Naive RAG의 한계

```
흔한 실패 케이스:

1. 검색 실패 (Retrieval Failure)
   - 질문과 문서가 다른 표현 사용
   - "월세 계약" 질문 → "임대차 계약" 문서 검색 실패

2. 맥락 부족 (Lost in Middle)
   - 긴 컨텍스트에서 중간 정보 무시됨

3. 환각 (Hallucination)
   - 검색된 문서와 모순된 답변

4. 낮은 정밀도 (Low Precision)
   - 관련 없는 청크도 검색됨
```

---

## 💡 핵심 포인트
- RAG = 검색(Retrieve) + 증강(Augment) + 생성(Generate)
- Indexing: 문서를 청크 → 임베딩 → 벡터저장소 저장 (1회성)
- Querying: 질문 임베딩 → 유사도 검색 → LLM 답변 생성 (매 질문마다)
- 문서 전처리 품질이 RAG 전체 성능에 직접 영향

## ⚠️ 주의사항
- 청크 크기: 너무 작으면 맥락 부족, 너무 크면 정보 희석
- 메타데이터는 필터링과 인용에 필수 → 처음부터 잘 설계
- Naive RAG는 시작점일 뿐, 실서비스에는 Advanced RAG 필요
